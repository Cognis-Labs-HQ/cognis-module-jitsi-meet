# Jitsi Meet モジュール

Jitsi Meet は、参加者選択、Messages チャット、セッション引き継ぎ、範囲を限定した共有、任意の同期 Whiteboard を備えた Cognis ミーティングルームを提供します。外部サービスは ctx 経由で解決し、API、ブラウザーリソース、保存処理はモジュールが所有します。

## 使用例

- 管理 → モジュールで HTTP(S) の Jitsi インスタンス URL を設定し、有効化テストを実行して Jitsi Meet を有効にします。管理 → Meetings には開催中と予定されているミーティングが表示されます。
- Meetings を開き、参加者を選択してルームを開始または参加します。プロフィールに依存する操作には公開されたハンドルが必要です。ハンドルが利用できなくなっても、既存のアクティブな参加関係は認証済みアカウントの識別情報から検索できます。
- 利用可能な参加者を開催中のミーティングにドラッグすると Share の承認を求めます。拒否されると参加者を利用可能リストに戻してトーストを表示します。
- Whiteboard でミーティングのキャンバスを開き、Whiteboard を閉じるで閉じます。画面共有中は説明ツールチップを付けてコントロールを無効にします。リンク共有ゲストはコントロールを表示せず、主催者の状態に従います。

ブラウザーの呼び出し元は、ホストが初期化したコンテキストから VoIP 連携を取得します。

```js
const startCall = uiCtx.capabilities.get("voip:startCall");
const action = await startCall({
    source: "messages",
    room: { id: roomId, kind: "group" },
    users: members,
    supportedActions: ["component"],
});
```

返されたアクションは Meetings コンポーネントを表し、呼び出し元はホストの Component Page 契約を使って起動します。

## 技術仕様

### 連携とアクション Flow

`bootstrap.js` は、モジュール所有のルート、UI 登録、公開 Capability `jitsi-meet:getMeetingChat`、ブラウザー Provider `voip:startCall`、既存のホストのミーティング・共有・ユーザー削除 Flow のフックを登録します。モジュールは非特権で、必要なコンポーネント UUID と Capability を Manifest に宣言します。任意の Whiteboard サービスは動的に検出し、有効化を妨げません。

有効なモジュールの非同期保存操作は、`initialize-store` と `execute-action` ステージを持つモジュール所有の `jitsi-meet:*` Flow を実行します。ルートの認可と検証は API 境界に残し、所有者のハンドラーが実際の操作を行います。内部の保存呼び出しはトランザクション境界を維持します。実行結果がない場合はエラーです。テストは、非同期アクションの完全なカタログ、所有者ステージの実際の実行、エラーの伝播を公開契約のローカル Fake で検証します。

制限された `api/disabled.js` エントリポイントは、機能ルートや UI を開始せず、設定と有効化テストを登録します。Cognis は無効なモジュールの Flow を登録しないため、このライフサイクル設定は同じ注入済み Store を直接使います。アンインストールは設定と、任意で保存済みモジュールデータを削除します。Cognis はモジュール無効化時に、ホストがスコープ管理するルート、Capability、Flow、フックの登録を削除します。

### 設定と API アクセス

全エンドポイントは `/api/v1/modules/jitsi-meet` を使います。設定の `GET` はユーザー権限、`PUT`、`DELETE`、`/admin/enable-test` は管理者権限を要求し、無効時にも使用できます。設定は HTTP(S) のインスタンス URL を検証します。有効化テストは設定済みサービスの応答を要求します。設定した Origin はホストの CSP Origin Capability に渡します。既存インスタンスの変更は、データベーストランザクションでモジュール所有のミーティングデータを消去します。

作成、参加、プレゼンス、状態、パスワード取得、セッション引き継ぎ、参加者変更、チャット概要、永続ミーティングからの退出、Whiteboard 変更は、認証済みアクセスとミーティングの認可を要求します。管理用一覧には管理者権限が必要です。プロフィールの識別と Messages、Share、通知、カレンダーデータはホストの Capability を使います。Share ゲストは操作が要求する正確なリソース Capability を持つ必要があり、権限拒否後にその Capability を省略して再試行しません。ユーザー共有とブロック関係はホストのアクセス契約で確認します。ゲストのマウントはアカウントプロフィールや参加者検索を呼び出しません。

### ミーティングの識別と保存

ミーティング ID とパスワードは暗号学的乱数を使います。名前はホストが生成する、各語の先頭を大文字にした 4 語のパスフレーズで、ルーム Slug、URL、明示的な Jitsi ルーム名に再利用します。初期化で既存の識別情報を再生成しません。永続ミーティングは正規化された元の参加者集合全体で検索し、メンバー変更やプロセス再起動を経てもルームとパスワードを保持します。認証情報と状態は、ホストが注入するデータベース Executor と範囲を限定した暗号化によってモジュール所有の保存領域を使用します。

保存したミーティングは一意の Messages `chat_room_id` を所有します。別の保存ミーティングの作成では `reuseExisting: false` を指定し、再開時は既存ルームを維持します。参加・退出ではルームの識別情報を変えずメンバーシップを更新します。`jitsi_chat_calls` は会話ごとに一つの使い捨て通話を別途予約します。割り当てと予約はトランザクションで処理し、競合時に孤立した行を残しません。直列化したスキーマ初期化で設定とライフサイクル要求の競合を防ぎます。

Heartbeat が途切れるとプレゼンスは期限切れになります。参加は同じアカウントの他のミーティングセッションを無効にし、終了したミーティングは残留プレゼンスを無視します。招待参加者のいないミーティングは使い捨てで、終了時に所有するチャットとミーティングを削除します。Messages から開始した通話は元の会話を保持します。退出したリンク共有ゲストは退出済みオーバーレイに留まります。使い捨てミーティングの終了では共有も削除します。

### 任意の Whiteboard 契約

Nextcloud Whiteboard はソフト依存関係です。ブラウザーはホスト UI コンテキストの初期化後に `whiteboard:uiGateway` と Floating Window の Capability を検出します。キャンバスファクトリーがコントロールの可用性を決め、存在しなければコントロールを表示しません。有効化操作は作成前にサーバーの可用性エンドポイントを確認します。サーバー検証には公開された `whiteboard:fetchBoardData`、`whiteboard:membership`、`whiteboard:deleteCanvas` 契約が必要です。可用性診断には Provider のバージョン、整合性、信頼情報を含めます。

Jitsi は公開 Gateway メソッド `requestCanvasPage({signal})` と `openCanvas({whiteboardId, elementId, signal})` を使用します。Whiteboard Provider がルート ID、キャンバス配置、通信とセッションの意味を所有します。Jitsi は正確な Board ID と自身のマウント先だけを指定し、終了時にウィンドウを解放します。メンバー変更はサーバーが所有する公開メンバーシップ契約を使用します。 Jitsi は埋め込みコンポーネントのコンテナーを会議の表示領域に制限し、マウントしたルートを明確な大きさのグリッド行に伸ばします。サイズを封じ込めたプロバイダーの表示を維持し、固有サイズが会議ウィンドウを拡大しないようにします。

有効な Whiteboard Provider の公開 UI 契約が不完全な場合、説明のツールチップ付きの無効なボタンを表示し、不足する Capability メソッドを記録します。Provider の読み込み失敗も説明します。任意 Provider が存在しない場合はボタンを表示しません。Avatar の在席情報は Whiteboard の準備状態とは独立しており、プロフィール在席情報の 404 はボタンを無効化しません。

永続ミーティングには `createCanvas` を使用し、明示的に一時ミーティングと指定された場合だけ `createDisposableCanvas` を使用します。参加者数や招待リストの変更でキャンバスの保持設定は変わりません。ミーティングを再度開くと、対応する保存済みキャンバスを再利用します。 関連付けは正確な Board ID、ミーティングのタイトル、期待する作成者アカウントと一致する必要があります。メンバーシップ更新は実際の Board 所有者と正規の参加者アカウント ID を解決します。リンクゲストは検証済みの関連付けだけを再利用し、作成や置換を行いません。Share は、正確なミーティングと Board の関係が開いている間だけアクセスを委任します。

主催者はすぐに開けます。他の参加者は Share の承認を通じて、出席中の主催者以外の参加者の厳密な過半数を必要とします。画面共有中は開けません。親ページでの Keyring 認可を、埋め込みウィンドウの起動より先に行います。自動で開く操作はブラウザーのユーザーアクティベーションを待ち、失敗した自動操作を同じ Board で繰り返しません。再試行の待機は上限付きで中止可能です。中止はタイマーとリスナーを解除し、次の生成を防ぎます。

同時のキャンバス準備は保留中のファクトリー操作を共有します。同期に失敗した場合は、再マウントでも未確認キャンバスを再利用できます。異なる Provider インスタンスには独立したキャッシュを使います。移動やミーティング変更後に届いた結果は現在の Trigger を変更できません。

開催中のミーティングへの参加は、チャットの選択に関係なく、参加応答を返す前に認可済みアカウントの開いた永続 Whiteboard へのメンバーシップを復元します。アカウントによる自動表示は `jitsi-meet:followWhiteboard` を実行し、正確な開いた関連付けを検証し、所有者認可によるメンバーシップを付与して、マウント前に関連付けを再確認します。追従は新たな承認投票を開始せず、開いた状態を変更しません。閉じた Board や置き換えられた Board はエラー表示なしで中止します。リンクゲストは委任されたアクセスを維持し、閉じた関連付けが任意 Provider を参加の必須条件にすることはありません。

読み込み、Keyring の解決、認証やセッション引き継ぎの待機、および埋め込み会議中はミーティング選択をロックします。参加要求は保留中の処理を共有し、中止や古い応答は現在の対象を置き換えません。認証待機中も、現在の出席情報を持つ認可済み招待ミーティングをアクティブ一覧に含めます。永続ミーティングを再開すると、所有者が認可する公開メンバーシップ契約で保存済みキャンバスを復元します。任意のキャンバスが利用できないか削除されている場合は記録し、ミーティング参加を妨げません。

### UI のマウントと会議セッション

Meetings は Cognis の Page Composer、SPA Router、ホスト初期化済み UI コンテキスト、`ui:reuse` を使います。モジュール CSS は Jitsi 所有の表示領域とコントロールを対象とし、Composer の表示を上書きしません。埋め込みマウントは `focusState` の `meetingId` を受け取り、ナビゲーションを重複表示しません。アクティブなマウントだけが `.jitsi-route-root` を設定し、中止はその設定とモジュール所有の Observer、タイマー、Handler、会議処理を解除します。ポーリングは結果適用前にマウントの寿命、要求順序、ミーティングの識別を確認し、終了とセッション引き継ぎにも適用します。成功した空の応答はロード表示を終え、変更のない応答は参加者 DOM を保持します。

Whiteboard はホストのコンポーネントページブローカーでマウントします。PiP はホストのフローティングウィンドウのツールバーとブラウザーの最上位レイヤーを使い、元の DOM 階層、テーマ、書体を保持します。オーバーレイ、状態操作、事前確認表示、招待のドロップ領域はアクティブな会議フレームに追従し、解除時に元の位置へ戻ります。通常サイズの一人だけの状態では、退出・残る操作とともに見出し、無効な開始ボタン、事前確認状態を保持します。最小サイズに収めるため、PiP のみでこれらの追加要素を非表示にし、メインウィンドウへ戻ると復元します。最小サイズは 400 × 225 で、三人目が参加すると一度だけ 500 × 282 に増やします。ドラッグ中止、Escape、フォーカス喪失時は招待領域を解除します。参加済みのユーザーは別のアクティブ会議へ切り替えられません。同時の退出イベントは、フレーム終了・チャットのポーリング停止・状態更新を行う一つの終了処理を共有します。

埋め込み前に、モジュールは Jitsi の保存済み認証セッション ID だけを削除し、他の設定を保持します。ブラウザーストレージの拒否や不正なデータはログに記録し、参加を妨げません。DOM の移動で再接続した場合、以前に参加に成功したセッションは解決済みパスワードを再送信できます。参加成功前の繰り返しの拒否では、引き続き新しい Keyring 値を求めます。開始操作は、事前確認から参加試行までホストの Page Loading Token を保持します。

### クリーンアップとリリース検証

削除したアカウントが保持する会議の主催者だった場合、正規化したハンドル順で最初の残存参加者へ所有権を移します。主催者がすでに参加者一覧から退出した場合も対象です。他の主催者とチャットルームの識別情報は維持します。

永続ミーティングの最後の退出とアカウント削除は、所有者認可による共通の外部リソース削除を使います。存在しないリソースはログに記録して処理を続け、それ以外のエラーはミーティング行の削除前に伝播します。アカウント削除は元の参加者と現在の参加者を更新し、利用可能なルームを残して利用不能なミーティングを削除します。共通のカタログは子テーブルから先に処理し、プレゼンス、状態、参加者、使い捨て通話予約を含めます。

モジュールは Manifest、Package、Lockfile のバージョンを同期し、パッケージ内の SHA-256 Hash を検証します。テストはモジュール内の公開契約 Fake を使い、コンポーネント分離、Namespace の所有権、ソースサイズ、ドキュメント構造、言語間の対応を確認します。リリースノートは PR ごとにドイツ語、英語、インドネシア語、日本語の単一変更履歴セットを使用します。

可用性応答のバージョン情報は診断です。`testedProvider` は検証したリリース、`provider.version` はホストの保証から取得した導入済みリリースを示します。公開機能の有無が可用性を決め、未実装の最小バージョン判定は行いません。Nextcloud 以外も同じ中立的契約を実装できます。

### モジュール構造とライフサイクル

API 登録は `api/index.js`、ドメインハンドラーは `api/routes/<domain>/index.js`、CSS は `ui/styles/`、マークアップは `ui/templates/` に配置します。テンプレート由来の AGENTS.md に従い、ローカルスクリプトは `npm --prefix <checkout> test`、導入済み操作は `cognisctl modules:jitsi-meet:ping` を使います。ブラウザープロバイダーは `mountProvider(scopedUiCtx)` を公開し、限定されたフロー、機能、リスナーを使います。ナビゲーションは `ui:navbarLinks` に登録します。Health と Keyring の登録が返す解除関数を `ctx.registerDisposer` に渡します。Keyring リセットはパスワード配送記録を消して再配送を可能にし、ミーティング、メンバーシップ、キャンバスを維持します。

ブラウザー検証は Playwright を使わず、導入済み Chromium の CDP を利用します。`CHROMIUM_EXECUTABLE_PATH=/path/to/chromium npm --prefix <checkout> run test:browser` を実行します。`npm run manifest:hashes` で再生成し、`npm run check:manifest` で検証します。リリースメタデータは `docs/changelog/` に置き、パッケージのハッシュには含めません。

Marketplace バナーは Cognis とプロバイダーのブランドを中央の切り抜きに強いレイアウトで組み合わせ、既存のプロバイダーアイコンを維持します。

## 会議の管理と復旧

管理 → 会議では「開催中」「すべての会議」「問題あり」のピルフィルターを提供します。管理者専用の一覧はスキーマ初期化を必要とせず既存の記録を読み取り、参加者の組み合わせやURLの重複、チャットルーム・キャンバスの重複参照を表示します。パスワードは公開しません。「終了」はCognisの参加状態を終了し、接続中のCognisクライアントの会議を閉じます。独立して参加したJitsi会議を管理する操作ではありません。開催中の会議は削除前に終了する必要があります。「削除」は会議の記録と共有を削除し、他の会議が参照していないチャットルームとキャンバスも削除します。処理が失敗した場合は再試行のため会議の記録を保持します。既に存在しないリソースは処理を妨げません。重複参照の削除により一意性エラーのキャッシュが解除され、通常のスキーマ初期化を再試行できます。管理者以外のルートでは通常のスキーマ検証を維持します。会議の取得に失敗した場合は自動更新を停止し、エラーを通知します。

## 連携元の排他的な参照設定

会議チャットはMessagesの解決機能に `source: {sourceType: "meeting", sourceId: meeting.id}` を渡します。キャンバスを有効化する際は `whiteboard:sourceBinding` で同じ識別情報を設定します。プロバイダーが他の会議との競合を拒否し、Jitsiは他のプロバイダーの保存列を変更しません。管理者による削除では、古い別の参照が残る場合、削除対象の会議の参照設定だけを解除します。Messagesから開始した通話の終了処理は元の会話を保持し、参照設定を解除します。新規通話のチャット設定に失敗した場合、作成した会議の記録を取り消します。Messagesの参照設定機能は必須です。Whiteboardは任意ですが、参照設定の契約が利用できる場合に限り有効です。

設定と有効化は設定テーブルだけを初期化します。会議データの整合性エラーがあってもモジュールを有効化し、管理画面から復旧できます。管理画面は検査に必要な参加者履歴の補助テーブルだけを初期化し、会議の制約を維持します。

## 見やすいミーティング管理

アクティブと今後のミーティングを、間隔を設けた同じパネルに表示します。名前、ID、展開できるチャットとキャンバスの参照をまとめ、問題は小さなピルで表示して参加者、活動、操作のスペースを確保します。フィルターはホストの標準ボタンを使用し、ホバー時に位置が動きません。今後の一覧には、非アクティブで終了しておらず、有効な未来の予定日時があるミーティングだけを表示します。過去の予定、日時なし、不正な日時のレコードは、すべてのミーティングから確認できます。

## 安定したミーティングのキャンバス識別子

Jitsi はミーティングの UUID を `resourceId`、`meeting` を `resourceType` として渡し、表示名はタイトルとしてだけ使います。同じミーティングを再度開くと、名前が変わっても同じ汎用参照を要求します。Whiteboard は Jitsi の内部実装を知らずに、保持、アクセス確認、同時リクエストの参照解決を管理します。

## 参加確認後の一人だけのミーティング通知

一人だけの通知は、招待数やメンバー数ではなく、ローカルの Jitsi 会議への参加確認と現在の在席状況に基づきます。参加や認証後の既存の待機期間と、残る操作による非表示を維持し、別の参加者が入ってから退出すると再び通知します。認証待ちの間は一人だけの通知を表示しません。Jitsi が参加を確認した後は、古い認証状態で通知を置き換えません。メインウィンドウと PiP の外観と配置は変更しません。

## 参加者の組み合わせごとに一つのミーティング識別子

作成時は、呼び出し元のコンテキストにかかわらず、正規化した現在または元の参加者が一致するデータベース内のミーティングを再利用します。forceNew オプションは廃止しました。作成時の参加者キーを固定し、競合を無視するアトミックな挿入により、同時リクエストにも同じ ID を返します。メンバー変更でもキーを保持し、検索と検出の固定件数制限をなくしました。過去の一致候補では一つだけのアクティブなミーティングを優先し、複数がアクティブなら管理者による修復を求めます。再利用では要求されたメンバーを復元し、既存のチャット関連付けを置き換えません。認証待ちの参加者は同じミーティングの在席情報と状態確認を維持し、完了後に同じ ID に参加します。Jitsi の参加確認時は、古い認証フラグがあっても定期的な在席更新を開始します。ミーティング一覧は参加処理中と会議中にブロックし、禁止カーソルと操作できないカードを使用します。

## 削除されたミーティングとキャンバス参照の回復

明示的にキャンバスを開く際は、準備済み ID を信用せず汎用の提供元参照を再解決します。存在しないキャンバスを提供元で新規作成し、ミーティングに関連付け直します。承認済みで開いていたキャンバスは、提供元が旧キャンバスの不存在と置換先の正確なリソース種別と識別子を確認した場合だけ、再投票なしで置き換えます。削除されたミーティングの明示的な起動では、読み込み済みの参加者情報と通常の一意な作成処理を使い、一時設定を維持して置換先 ID に参加します。不明な参照、ゲスト、権限やサービスのエラーから新しいリソースを推測しません。削除済み内容は復元せず、回数を制限した処理で新しい項目を作り、成功を通知します。

直接読み込まれたMeetingsページは、ホストがルート変更を実行したとき、またはドキュメントを離れたときにマウントを中断します。会議検索のポーリングはこのマウントに属し、中断時に停止して以後は再開しません。遅れて届く応答や中断されたリクエストは、移動先のページを更新したり会議のエラーを表示したりできません。取り消されたナビゲーションでは現在のページを維持します。

参照はComponentsと同じホストの折りたたみセクションコンポーザーを使用します。会議と今後の会議の定期更新でも開いた参照を維持し、キーボード操作に対応します。進行中の会議、すべての会議、問題のある会議の各フィルターに専用の空状態メッセージを表示します。

キャンバスの参照元の確保は承認後、直列化された状態更新内で行います。メンバー同期や保存が失敗すると新しい確保を解除し、既存の関連付けは維持します。通常の会議作成では一時通話を作成せず、通話の復元には既存の会話のVoIPルートを使用します。後続に置き換えられた会議予定の応答は破棄します。直接ページは独立したコントローラーではなくホストのライフサイクルシグナルを使用します。

## 会議検索中の接続断への対応

ネットワーク障害が発生すると会議検索の定期取得を停止し、タイマーからの Promise 拒否を処理します。オフラインまたはキャンセルされたリクエストでは検索エラーのトーストを表示せず、最後の会議一覧を保持します。ホストの任意のオフライン状態機能を使用し、後処理はページのシグナルに紐付けます。 進行中の会議のプレゼンスと状態の定期取得も同じライフサイクルに従い、バックグラウンドのリクエストが失敗すると両方を停止します。
