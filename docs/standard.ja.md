# Jitsi Meet モジュール

Jitsi Meet モジュールは、参加者選択、再利用可能なミーティングルーム、セッション再取得、Messages チャット連携、オプションの共有 Whiteboard を備えた Cognis ネイティブのミーティング管理を提供します。

## 使用例

- ページ全体を遷移せずに `/meetings` と `/meeting` からミーティングへ参加または再接続する。
- 参加者を選択し、ミーティングアクセスを共有し、ミーティングの Messages チャットを使用する。別のミーティングに実際に参加中のユーザーは参加者検索に表示されず、進行中のミーティングへドラッグして追加することもできません。予定済みの招待だけでは利用不可になりません。利用可能な参加者と進行中のミーティングは5秒ごとに更新され、SPA ナビゲーション後の在席インジケーターも再読み込みされます。参加者検索では Cognis core の `user` 結果フィルターを渡し、進行中ミーティングの一覧は初期オーバーレイの「ミーティングを開始」ボタン直上にのみ表示します。 通知から受け取ったミーティングパラメーターは処理後すぐ URL から削除します。参加者をドラッグしていない状態でウィンドウフォーカスが変わっても現在のオーバーレイ表示を維持するため、待機中のロビーから引き続きミーティングを開始できます。通知経由の参加を含め、ミーティングを選択または参加している間は進行中ミーティング欄を常にロックし、ミーティング終了通知には操作リンクもメールリンクも含めません。 参加者ペインでは、左側 30% の縦スクロール列に利用可能な既知ユーザーを配置し、残り 70% に横スクロール可能な永続ミーティングカードを表示します。各カードは安定した名前を上部中央に置き、標準プロファイルアバターを最大10人まで周囲に配置し、そのミーティングが進行中の場合はアプリグリーンの色区間が境界に沿って移動します。 カードは内容に合わせたコンパクトなクリック操作です。選択すると参加者一覧をステージへ復元してそこまでスクロールし、「ミーティングを開始」で安定したミーティングを再利用できます。3秒間長押しすると緑の色合いが赤へ変わって確認を開き、現在のユーザーを削除し、最後のメンバーが退出した時点でミーティング、チャットルーム、関連付けられた Whiteboard を完全に削除します。 「以前のミーティング」カードはタイトルと折り返されたアバター行に合わせた高さとなり、縦方向のオーバーフローを発生させません。進行中の状態はカード境界に沿って移動する色の区間だけで示し、削除の長押しを開始すると一定の不透明度で緑から赤へのグラデーションが直ちに始まります。確認には破壊的操作と中立操作のボタン表示を使用し、退出完了は情報通知として表示します。 「参加者を検索」は利用可能な参加者の先頭に疑問符付きプロフィールアバターとして表示します。共通の参加者見出しは両方の列の上に置き、利用可能な参加者と「以前のミーティング」のタイトルを揃えます。コンテンツ高のギャラリーは縦方向のオーバーフローを抑え、削除の長押しでは最初のポインター押下フレームから一定の不透明度のグラデーションを確実にアニメーションします。 参加者見出しは外側余白をゼロにしたまま継承された自然な文字高を維持します。ペインは見出し領域を独立して確保し、参加者レイアウトは強制的な見出しサイズに圧迫されず、親要素の残り領域へ柔軟に収まります。「以前のミーティング」はスクロールバーを視覚的に非表示にしたまま、ポインター、タッチ、ホイール、キーボードで横方向にスクロールできます。 ステージ上の参加者は、プロフィールリンク以外をクリックするか「参加可能なユーザー」へドラッグして戻せます。「以前の会議」から復元した参加者構成を変更した場合、「会議を開始」は変更後の構成に対応する固定会議名を読み込まず、新しい会議室を作成します。 参加可能なユーザーがいない場合は、空の一覧とともに「参加者を検索」アバターも非表示になります。 アクティブな「以前の会議」の表示は、より太く長く明るい緑のセグメント、強い発光、カード周囲を速く巡回するアニメーションを使用します。 ポインターをどこで離しても未完了の参加者ドラッグを終了し、ステージのドロップ領域を閉じます。「以前の会議」には正規化した参加者構成ごとに1枚だけカードを表示し、アクティブな会議室を優先するため、同じ構成への追加を繰り返しても重複した履歴カードが増えません。 元の参加者構成は現在のメンバーシップとは別に記録されます。「以前の会議」にはその安定した構成が引き続き表示され、進行中の会議で参加者が追加または削除された後でも、開始時には同じ会議 ID と暗号化チャット履歴が再利用されます。
- 破棄されないミーティングの進行中は、別の利用可能なユーザーをミーティングウィンドウへドラッグして参加者として永続的に追加できます。Cognis は正規の実行者アカウント ID とユーザーアカウント ID を指定する `social:messages:membership` capability を介して暗号化された Messages チャットへのアクセスを用意し、招待を送り、そのユーザーが参加時にミーティングパスワードを取得できるようにします。認証済みユーザーが参加するたびに、チャットを読み込む前に冪等なメンバーシップ操作を再適用し、その参加者が以前ミーティングチャットを退出またはアーカイブしていてもアクセスを復元します。参加者情報を更新しても進行中のミーティングがロビーオーバーレイで覆われることはなく、利用可能な参加者がいない場合は明示されます。進行中のミーティングで利用可能なユーザーをドラッグすると、埋め込みウィンドウと完全に同じ境界のローカライズされたドロップ先が表示されます。ドラッグ中は埋め込みより前面に移動し、ドロップまたはドラッグ終了後は背面に戻ります。参加者をドラッグしている間は、緑色の内側アウトラインと破線のドロップ先が常に表示されます。実際に参加中のユーザーが 1 人だけの場合、新しい参加者の招待は不在の参加者に合意を求めず直ちに承認されます。進行中の招待が成功するとトーストを表示し、Messages API で既存の暗号化チャットルームのメンバーを更新し、状態ポーリング時に同じチャットを再描画し、既存の永続 Whiteboard を、正規の実行者およびユーザーのアカウント ID を指定する `whiteboard:membership` で更新します。ミーティング API は、参加者変更を保存する前に既存ルームのメンバー更新を完了するため、クライアントが別のルーム ID へ切り替わることはありません。Jitsi がローカル参加者の削除を通知すると、認証済みユーザーは保存済み参加者一覧から削除され、再招待できる状態になります。ゲストの場合は、そのゲストが使用した Share リンクだけが失効します。 サーバー側のユーザー名とハンドルの正規化はすべて公開 capability `social:profile:identity` に委譲し、各正規化呼び出しへ capability を明示的に渡します。モジュール独自の正規化規則は保持しません。 チャットルームのクリーンアップは、`roomId` と正規の `actorAccountId` を指定する公開 Capability `social:messages:deleteChatroom` を使用します。Messages はルーム作成者または唯一残った参加者を認可し、依存するチャットレコードをトランザクションで削除します。 ミーティングの破棄中に、参照先の Whiteboard またはチャットルームが標準の未検出ステータス、コード、メッセージを返した場合は、すでに削除済みとして扱います。フォールバックを構造化されたリソースメタデータとともに記録し、残りのリソースとミーティングレコードのクリーンアップを続行します。 最新の Messages 連携は削除を Flow 対応の公開 Capability として提供します。Jitsi は `social:messages:deleteChatroom` を必須として宣言し、API 登録時に呼び出し可能な関数へ解決されることを検証するため、クリーンアップ時の遅いエラーではなく早期に失敗します。 主催者が進行中の会議へ参加者を追加すると、所有者のクライアントからも Whiteboard UI ゲートウェイを通じて参加者全員のアクセスを再同期します。主催者以外からのオープン要求には Share の承認を使用し、受動的な状態投票だけに依存せず、ほかのすべてのアクティブなアカウント参加者へ合意確認を表示します。 Whiteboard の承認リクエストを送信すると情報トーストを表示します。会議の所有者がほかのメンバーより先に退出した場合は、所有権メタデータを保持したままチャットのメンバー資格を削除するため、最後に残ったメンバーが認可された唯一の参加者としてチャットを削除できます。
- Whiteboard 操作は開ける状態では確認スタイルを使用し、「Whiteboard を閉じる」の表示中はキャンセルスタイルへ切り替わります。Jitsi がローカルまたはリモート参加者の画面共有を通知すると、共有 Whiteboard は全員に対して閉じ、画面共有が終了するまで無効になります。Whiteboard のためにミーティングが PiP へ移ると、進行中参加者のドロップ先を含むミーティングオーバーレイもフローティング表示内へ移動し、PiP を閉じるとステージへ戻ります。参加者のドラッグごとに、ドロップ先を表示する前に現在のオーバーレイホストを再確認します。フローティング Jitsi フレームへ移動したドロップ先には絶対配置のインセット境界を適用し、PiP ウィンドウ全体を引き続き覆います。
- Administration → Meetings で進行中および予定されたミーティングを監視する。
- Meetings ルートをオーバーレイ、全画面、またはピクチャーインピクチャーのコンポーネントページとして埋め込む。

通知するピクチャーインピクチャーの最小サイズは 400 × 225 ピクセルで、Jitsi Meet が対応する最小モバイル領域 320 × 180 より 25% 大きくしています。ミーティングがフローティング表示中の場合、進行中の参加者が3人目になると両方の最小寸法を一度だけ 25% 増やして 500 × 282 ピクセルにします。それ以上の参加者では拡大せず、モジュールがホストのフローティングウィンドウ解放関数を通じてこの1回の変更を適用します。

## 技術仕様

- API 呼び出しには有効な Cognis アクセストークンが必要で、ミーティング詳細は承認済み参加者またはスコープ付き共有ゲストにのみ返されます。 進行中ミーティングの検索では、現在解決可能なプロファイルハンドルがないアカウントでも認証済みアカウント ID によって参加者メンバーシップを認可するため、その参加者を含み Cognis が進行中と判断したすべてのミーティングが引き続き表示されます。プロファイル依存のミーティング操作は引き続き利用できません。制限付き共有マウントは Share のゲストプロフィールだけで ID を解決し、アカウントプロフィールや参加者検索エンドポイントを要求しません。ゲスト参加でもミーティングパスワードと暗号化チャットのキーリング解決を維持します。既存の Whiteboard 関連付けがないゲストは、効果のないキャンバス準備を繰り返しスケジュールせず、同期されたミーティング状態を待機します。
- パスワードはミーティングレコードごとに生成されます。ミーティング名には、ホストの `reuse:generatePassphrase` capability で生成したタイトルケースの4語パスフレーズを使用します。同じハイフン区切りの名前を表示名と Jitsi ルームスラッグとして保存し、ミーティング URL に含め、常に `JitsiMeetExternalAPI` へ明示的に渡します。モジュールが Jitsi にルーム名の生成や報告を要求することはありません。スキーマ初期化が既存のミーティング名、URL、ルームスラッグを再生成または上書きすることはありません。この名前はミーティング一覧、Messages チャット、共有、Whiteboard にも伝播します。永続ミーティングは正規化済みの全参加者セットで解決し、進行中のメンバー変更後も含め、プロセス再起動後に同じ保存済みミーティング ID、名前、URL、ルームスラッグ、パスワード、Messages ルームを再利用します。参加者のいないミーティングは破棄可能で、毎回新しい ID と単一メンバーの Messages チャットを作成し、終了時にチャットとミーティングレコードの両方を完全に削除します。認証済みの設定 `DELETE` エンドポイントはモジュールが無効な間も利用できるため、管理者は無効な Jitsi URL を消去できます。
- モジュール所有の永続化領域に、設定、参加者、在席、ライフサイクル状態、Whiteboard 状態、合意投票を保存します。 新規インストール時のスキーマ初期化をデータベース Executor ごとに直列化し、ライフサイクル要求と設定要求が同時に PostgreSQL テーブルを作成しないようにしました。スキーマ作成と認証情報のバックフィルは専用のストアスキーマモジュールに置き、メインストアにはミーティング、状態、在席の操作を維持します。
- セッション再取得時には、ユーザーの以前のアクティブなミーティングセッションを切断します。

### 統合契約

- `bootstrap.js` が唯一のプラットフォームエントリポイントであり、ctx 機能とフローがコンポーネント間の唯一の統合面です。
- ルーティング、共有、埋め込みの各 Meetings マウントは、ライフサイクルシグナルが有効な間だけ `.jitsi-route-root` を使用します。すでに中止されたマウントは永続的な Cognis アプリルートを取得せず、進行中のマウントを中止すると、このクラスとモジュール所有の Observer、イベントハンドラー、タイマー、埋め込みミーティング処理が解除されます。
- Meetings SPA は Cognis ルーターと Page Composer を使用します。埋め込み呼び出し元はシリアライズ可能な `meetingId` を `focusState` で渡し、埋め込みマウントはフレームレスでホストナビゲーションを重複させません。
- ブラウザユーティリティと共通スタイルシートの完全なカタログは、Meetings 画面を描画する前に必須の `ui:reuse` 機能から読み込みます。ミーティングフレームとオーバーレイ要素はモジュール DOM から解決し、Whiteboard プロバイダーの Capability ペイロードから読み取ることはありません。標準コントロール表示は Cognis core が提供し、モジュールはプロバイダー所有のスタイルシートを読み込まず、すべてのモジュール CSS セレクターを `.jitsi-route-root` 配下に限定します。未使用の旧ミーティングスタイルは配布しません。
- Nextcloud Whiteboard はソフトモジュール依存関係として宣言されるため、必須にすることなく管理者がインストール時に選択できます。モジュール所有のバックエンド可用性エンドポイントを全アカウントクライアント共通の表示判断とし、ブラウザの Capability 検出は承認済みコントロールの初期化だけを行います。オプションの連携は、基本の `whiteboard:uiGateway` キャンバスファクトリ、コンポーネントページ、フローティングウィンドウ機能が利用できる場合に表示します。ミーティング API は関連付けられたキャンバスの実際の所有者を解決し、参加者変更を保存する前に、正規のアカウント ID を指定して、所有者認可された `whiteboard:membership` の `add` と `remove` 関数を呼び出します。プロバイダー契約の `createCanvas` メソッドは招待済み参加者のハンドルを指定して通常のキャンバスを作成し、参加者のいないミーティングだけが `createDisposableCanvas` を使用します。Meetings は永続作成から破棄可能作成へフォールバックしません。関連付けを受け入れる前、またはアクセスを委任する前に、要求時点でスコープ付きまたはシステム ctx の Capability サーフェスからプロバイダーを解決し、識別子、ミーティング名、新規関連付けの場合は作成者を検証し、関連付け種別を保存し、不明または不一致の古い関連付けを置き換えて、ユーザーが明示的に開いた場合にのみ、検証済みの永続キャンバスを再利用します。共有リンクのゲストには表示コントロールやキャンバス作成 Capability を提供せず、非対話型の Whiteboard オーケストレーションによって主催者の同期された開閉状態に従わせ、既存のミーティング関連付けと完全に一致するものだけを再利用します。キャンバスの作成や関連付けの置換は要求しません。ミーティングに限定された Share ID によって同期状態を認可し、在席と合意投票には安定した ID を使用します。モジュールは汎用 Flow `resolve-share-delegated-access` を拡張し、Share が現在開いているミーティングとボードの完全一致する関係を検証できるようにします。Jitsi は委任された Whiteboard の読み取り・書き込み操作と必要なソース Capability `meeting:join` を宣言し、Share が元のゲストトークンを独立して検証します。
- 主催者は Whiteboard を直ちに開けます。その他の参加者には、現在参加中の主催者以外の厳格な過半数が必要です。オープン状態は現在のミーティングセッション内だけで同期され、参加中のユーザーが同じキャンバスを開いてミーティングをピクチャーインピクチャーへ移します。ミーティングの終了時にこの状態は解除され、永続キャンバスの関連付けだけを理由に新しいセッションで自動的に開くことはありません。
- Whiteboard コンポーネントを開く前に、Meetings は親ページでキーリングへのアクセスを要求し、ロック解除要求にポップアップホストを提供します。その後、Whiteboard はコンポーネントページブローカーから、ドキュメント所有のスクロールを使う埋め込みオーバーレイコンポーネントとして起動します。Meetings は表示用クラスを追加したり共有ページシェルを上書きしたりせず、インポート済みのコンポーネントページとボタンのクラスを使用します。
- Whiteboard コントロールは、隣接する共有コントロールと同じ標準の `<button>` です。既定では core の `btn-confirm` 表示を使い、アクティブ時はインポート済みの `active` と `btn-cancel` の状態を使い、ラベルを「Whiteboard を閉じる」に変更します。アクティブなコントロールを選択すると、ミーティングの Whiteboard が閉じます。Whiteboard の準備前に、プロバイダー capability はホストを通じて一度読み込まれます。コンポーネントウィンドウの一時的なマウント失敗は、コンポーネントページを再登録または置換せず、上限付き指数バックオフで再試行します。ロック解除の要求またはコンポーネントのマウントを待っている間、コントロールは通常の「ホワイトボード」ラベルのまま無効になり、コンポーネントウィンドウのマウント完了後にのみ「Whiteboard を閉じる」へ変わります。ミーティング状態の変更やナビゲーションによって取り消された古い処理は、エラートーストを表示せず破棄します。同期された自動オープンは現在のブラウザアクティベーション中に進行し、それ以外ではシグナルに紐づく入力リスナーが次のアクティベーションで処理を再開するため、キーリング要求とコンポーネント生成はブラウザに認可された状態を維持します。失敗した自動試行は同じボードで繰り返しません。実際の失敗では、段階、ミーティングとボードの ID、エラーメッセージ、完全な Error オブジェクトをホストログとブラウザコンソールの両方へ書き込み、ローカライズ済みトーストで失敗段階を示します。
- アクティブなミーティングのロビー表示は、ミーティングレコードの選択後にプリフライトオーバーレイを再表示しません。Whiteboard のピクチャーインピクチャーでミーティングフレームがホスト所有の `floating-window` 状態にある間、ミーティングオーバーレイと参加者招待ドロップゾーンは現在の DOM から解決され、そのフローティングフレームへ移動します。ピクチャーインピクチャーを閉じると通常のステージへ戻ります。ドラッグ終了、対象外へのドロップ、Escape、またはウィンドウのフォーカス喪失によるキャンセルでは、ドロップゾーンが必ず削除されます。
- アクティブな参加者招待のドラッグでは、別のポップアップを描画せず、通常のミーティングオーバーレイ構造と緑色のアクティブターゲット枠を再利用します。新しいミーティングの開始時は、プリフライトまたは作成処理の前に、モジュールが提供する `ui:reuse` のページエントリーリソースから Cognis core の `beginPageLoading()` トークンを取得し、Jitsi への参加試行が完了した後にのみ解放します。Cognis のコンポーネントページ生成には現在のブラウザユーザーアクティベーションが必要なため、同期されたアカウント Whiteboard は自動マウントを次のブラウザアクティベーションまで延期し、`whiteboard_component_window_unavailable` の再試行を繰り返しません。
- Jitsi の画面共有によって Whiteboard アクセスがロックされている間、無効な Whiteboard コントロールとそのスロットにはロック理由を説明するローカライズ済みホバータイトルが表示されます。現在のブラウザアクティベーションがない同期済みアカウント Whiteboard は、シグナルに紐づくポインターおよびキーボードリスナーを設定し、次のユーザーアクティベーションで自動的にマウントを続行します。ボードを閉じるかマウントを中止するとリスナーは削除されます。アクティブなミーティングへの参加者追加には Share の `share:requestApproval` Capability が必須で、明示的な最終承認後にのみ処理を続行します。拒否または未完了の判断では追加を中止し、承認処理の実行時エラーだけは構造化エラーログを残して意図的にフェイルオープンします。
- 利用可能なユーザーをアクティブなミーティングへドロップすると、そのユーザーを利用可能一覧から一時的に除外し、サーバー側の Share 合意要求を直ちに開始します。明示的に拒否された場合はユーザーを並び替え済みの利用可能プールへ戻し、招待者へローカライズ済みの拒否トーストを表示します。その他の要求失敗でも同じロールバックを行い、一般的な失敗トーストを表示します。ローカルユーザーがいずれかのミーティングへ参加中は、アクティブなミーティングのグリッド全体と各ミーティングボタンを無効にし、現在のミーティングが終了するまでクリックによる切り替えを拒否します。
- Whiteboard の PiP 移動は Cognis のホスト所有フローティングウィンドウツールバーに委譲します。`ui:makeFloatingWindow` の呼び出し時に `.jitsi-stage-header` を第2のドラッグハンドルとして渡しません。
- カンファレンス退出イベントは 1 回の破棄処理にまとめます。ミーティングフレームと Whiteboard を直ちに閉じ、再描画の前にミーティングチャットのポーリングタイマーとルーム ID を消去し、通常のオーバーレイを復元して参加者選択を消去し、破棄完了前にアクティブなミーティングと利用可能な参加者を更新します。永続 Whiteboard のアクセス拡張は初回同期時に現在の全メンバーをプロバイダーへ確認し、メンバー構成が変わるたびにアクセス拡張を繰り返します。
