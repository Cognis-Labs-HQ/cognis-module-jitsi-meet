# Jitsi Meet モジュール

Jitsi Meet モジュールは、参加者選択、再利用可能なミーティングルーム、セッション再取得、Messages チャット連携、オプションの共有 Whiteboard を備えた Cognis ネイティブのミーティング管理を提供します。

## 使用例

- ページ全体を遷移せずに `/meetings` と `/meeting` からミーティングへ参加または再接続する。
- 参加者を選択し、ミーティングアクセスを共有し、ミーティングの Messages チャットを使用する。
- Administration → Meetings で進行中および予定されたミーティングを監視する。
- Meetings ルートをオーバーレイ、全画面、またはピクチャーインピクチャーのコンポーネントページとして埋め込む。

## 技術仕様

- API 呼び出しには有効な Cognis アクセストークンが必要で、ミーティング詳細は承認済み参加者またはスコープ付き共有ゲストにのみ返されます。制限付き共有マウントは Share のゲストプロフィールだけで ID を解決し、アカウントプロフィールや参加者検索エンドポイントを要求しません。ゲスト参加でもミーティングパスワードと暗号化チャットのキーリング解決を維持します。既存の Whiteboard 関連付けがないゲストは、効果のないキャンバス準備を繰り返しスケジュールせず、同期されたミーティング状態を待機します。
- パスワードはミーティングレコードごとに生成されます。ミーティング名には、ホストの `reuse:generatePassphrase` capability で生成したタイトルケースの4語パスフレーズを使用します。同じハイフン区切りの名前を表示名と Jitsi ルームスラッグとして保存し、ミーティング URL に含め、常に `JitsiMeetExternalAPI` へ明示的に渡します。モジュールが Jitsi にルーム名の生成や報告を要求することはありません。この名前はミーティング一覧、Messages チャット、共有、Whiteboard にも伝播します。参加者のいないミーティングも作成時に単一メンバーの Messages チャットを受け取り、後から共有リンクのゲストが参加できます。このチャットは破棄可能なミーティングの終了時に完全に削除されます。認証済みの設定 `DELETE` エンドポイントはモジュールが無効な間も利用できるため、管理者は無効な Jitsi URL を消去できます。
- モジュール所有の永続化領域に、設定、参加者、在席、ライフサイクル状態、Whiteboard 状態、合意投票を保存します。 新規インストール時のスキーマ初期化をデータベース Executor ごとに直列化し、ライフサイクル要求と設定要求が同時に PostgreSQL テーブルを作成しないようにしました。スキーマ作成と認証情報のバックフィルは専用のストアスキーマモジュールに置き、メインストアにはミーティング、状態、在席の操作を維持します。
- セッション再取得時には、ユーザーの以前のアクティブなミーティングセッションを切断します。

### 統合契約

- `bootstrap.js` が唯一のプラットフォームエントリポイントであり、ctx 機能とフローがコンポーネント間の唯一の統合面です。
- Meetings SPA は Cognis ルーターと Page Composer を使用します。埋め込み呼び出し元はシリアライズ可能な `meetingId` を `focusState` で渡し、埋め込みマウントはフレームレスでホストナビゲーションを重複させません。
- ブラウザユーティリティと共通スタイルシートの完全なカタログは、Meetings 画面を描画する前に必須の `ui:reuse` 機能から読み込みます。標準コントロール表示は Cognis core が提供し、モジュールはプロバイダー所有のスタイルシートを読み込まず、すべてのモジュール CSS セレクターを `.jitsi-route-root` 配下に限定します。未使用の旧ミーティングスタイルは配布しません。
- Nextcloud Whiteboard はソフトモジュール依存関係として宣言されるため、必須にすることなく管理者がインストール時に選択できます。オプションの連携は、基本の `whiteboard:uiGateway` キャンバスファクトリ、コンポーネントページ、フローティングウィンドウ機能が利用できる場合に表示します。プロバイダー契約の `createCanvas` メソッドは招待済み参加者のハンドルを指定して通常のキャンバスを作成し、参加者のいないミーティングだけが `createDisposableCanvas` を使用します。Meetings は永続作成から破棄可能作成へフォールバックせず、関連付け種別を保存し、不明または不一致の古い関連付けを置き換えて、ユーザーが明示的に開いた場合にのみ、検証済みの永続キャンバスを再利用します。共有リンクのゲストにはキャンバス作成 Capability を要求せずに Whiteboard コントロールを表示し、既存のミーティング関連付けと完全に一致するものだけを再利用します。キャンバスの作成や関連付けの置換は要求しません。ミーティングに限定された Share ID によって同期状態を認可し、在席と合意投票には安定した ID を使用します。モジュールは汎用 Flow `resolve-share-delegated-access` を拡張し、Share が現在開いているミーティングとボードの完全一致する関係を検証できるようにします。Jitsi は委任された Whiteboard の読み取り・書き込み操作と必要なソース Capability `meeting:join` を宣言し、Share が元のゲストトークンを独立して検証します。
- 主催者は Whiteboard を直ちに開けます。その他の参加者には、現在参加中の主催者以外の厳格な過半数が必要です。オープン状態は現在のミーティングセッション内だけで同期され、参加中のユーザーが同じキャンバスを開いてミーティングをピクチャーインピクチャーへ移します。ミーティングの終了時にこの状態は解除され、永続キャンバスの関連付けだけを理由に新しいセッションで自動的に開くことはありません。
- Whiteboard コンポーネントを開く前に、Meetings は親ページでキーリングへのアクセスを要求し、ロック解除要求にポップアップホストを提供します。その後、Whiteboard はコンポーネントページブローカーから、ドキュメント所有のスクロールを使う埋め込みオーバーレイコンポーネントとして起動します。Meetings は表示用クラスを追加したり共有ページシェルを上書きしたりせず、インポート済みのコンポーネントページとボタンのクラスを使用します。
- Whiteboard コントロールは、隣接する共有コントロールと同じ標準の `<button>` です。既定では core の `btn-neutral` 表示を使い、アクティブ時はインポート済みの `active` と `btn-confirm` の状態を使い、ラベルを「Whiteboard を閉じる」に変更します。アクティブなコントロールを選択すると、ミーティングの Whiteboard が閉じます。Whiteboard の準備前に、プロバイダー capability はホストを通じて一度読み込まれます。コンポーネントウィンドウの一時的なマウント失敗は、コンポーネントページを再登録または置換せず、上限付き指数バックオフで再試行します。ロック解除の要求またはコンポーネントのマウントを待っている間、コントロールは通常の「ホワイトボード」ラベルのまま無効になり、コンポーネントウィンドウのマウント完了後にのみ「Whiteboard を閉じる」へ変わります。ミーティング状態の変更やナビゲーションによって取り消された古い処理は、エラートーストを表示せず破棄します。現在有効な準備またはマウントに失敗した場合、Meetings はエラーを記録して「ホワイトボードの読み込みエラー」を表示し、そのブラウザマウントのコントロールを無効にします。
