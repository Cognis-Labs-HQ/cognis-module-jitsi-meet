# Jitsi Meet モジュール

Jitsi Meet モジュールは、参加者選択、再利用可能なミーティングルーム、セッション再取得、Messages チャット連携、オプションの共有 Whiteboard を備えた Cognis ネイティブのミーティング管理を提供します。

## 使用例

- ページ全体を遷移せずに `/meetings` と `/meeting` からミーティングへ参加または再接続する。
- 参加者を選択し、ミーティングアクセスを共有し、ミーティングの Messages チャットを使用する。
- Administration → Meetings で進行中および予定されたミーティングを監視する。
- Meetings ルートをオーバーレイ、全画面、またはピクチャーインピクチャーのコンポーネントページとして埋め込む。

## 技術仕様

- API 呼び出しには有効な Cognis アクセストークンが必要で、ミーティング詳細は承認済み参加者またはスコープ付き共有ゲストにのみ返されます。
- パスワードはミーティングレコードごとに生成されます。新しいレコードは、主催者が Jitsi のサポートされたウェルカムフローを開くまでの間だけ、一意のフラグメント付き保留 URL を保持します。そこで `GENERATE_ROOMNAMES_ON_WELCOME_PAGE` が Jitsi 自身のランダムなルーム名を要求します。モジュールは `videoConferenceJoined` が報告したルームを取得して検証し、正規のミーティング名と URL として保存し、その正確な名前をミーティング一覧、Messages チャット、共有、Whiteboard に伝播します。参加者のいないミーティングも識別子取得後に単一メンバーの Messages チャットを受け取り、後から共有リンクのゲストが参加できます。このチャットは破棄可能なミーティングの終了時に完全に削除されます。スクリプトと iframe の起動は失敗処理と iframe 読み込みタイムアウトで保護されます。認証済みの設定 `DELETE` エンドポイントはモジュールが無効な間も利用できるため、管理者は無効な Jitsi URL を消去できます。
- モジュール所有の永続化領域に、設定、参加者、在席、ライフサイクル状態、Whiteboard 状態、合意投票を保存します。 新規インストール時のスキーマ初期化をデータベース Executor ごとに直列化し、ライフサイクル要求と設定要求が同時に PostgreSQL テーブルを作成しないようにしました。
- セッション再取得時には、ユーザーの以前のアクティブなミーティングセッションを切断します。

### 統合契約

- `bootstrap.js` が唯一のプラットフォームエントリポイントであり、ctx 機能とフローがコンポーネント間の唯一の統合面です。
- Meetings SPA は Cognis ルーターと Page Composer を使用します。埋め込み呼び出し元はシリアライズ可能な `meetingId` を `focusState` で渡し、埋め込みマウントはフレームレスでホストナビゲーションを重複させません。
- ブラウザユーティリティと共通スタイルシートの完全なカタログは、Meetings 画面を描画する前に必須の `ui:reuse` 機能から読み込みます。標準コントロール表示は Cognis core が提供し、モジュールはプロバイダー所有のスタイルシートを読み込まず、すべてのモジュール CSS セレクターを `.jitsi-route-root` 配下に限定します。未使用の旧ミーティングスタイルは配布しません。
- Nextcloud Whiteboard はソフトモジュール依存関係として宣言されるため、必須にすることなく管理者がインストール時に選択できます。オプションの連携は、基本の `whiteboard:uiGateway` キャンバスファクトリ、コンポーネントページ、フローティングウィンドウ機能が利用できる場合に表示します。プロバイダー契約の `createCanvas` メソッドは招待済み参加者のハンドルを指定して通常のキャンバスを作成し、参加者のいないミーティングだけが `createDisposableCanvas` を使用します。Meetings は永続作成から破棄可能作成へフォールバックせず、関連付け種別を保存し、不明または不一致の古い関連付けを置き換えて、ミーティングの読み込み時に検証済みの永続キャンバスを自動的に開きます。
- 主催者は Whiteboard を直ちに開けます。その他の参加者には、現在参加中の主催者以外の厳格な過半数が必要です。オープン状態は保存され、現在および後から参加するユーザーが同じキャンバスを自動的に開き、ミーティングをピクチャーインピクチャーへ移します。
- Whiteboard コンポーネントを開く前に、Meetings は親ページでキーリングへのアクセスを要求し、ロック解除要求にポップアップホストを提供します。その後、Whiteboard はコンポーネントページブローカーから、ドキュメント所有のスクロールを使う埋め込みオーバーレイコンポーネントとして起動します。Meetings は表示用クラスを追加したり共有ページシェルを上書きしたりせず、インポート済みのコンポーネントページとボタンのクラスを使用します。
- Whiteboard コントロールは、隣接する共有コントロールと同じ標準の `<button>` です。既定では core の `btn-neutral` 表示を使い、アクティブ時はインポート済みの `active` と `btn-confirm` の状態を使い、ラベルを「Whiteboard を閉じる」に変更します。アクティブなコントロールを選択すると、ミーティングの Whiteboard が閉じます。準備またはマウントに失敗した場合、Meetings はエラーを記録し、「ホワイトボードの読み込みエラー」を表示して、そのブラウザマウントではコントロールを無効にし、ポーリングによる再試行を防ぎます。再読み込み、または別ページへ移動して戻ると新しいマウントになり、再試行できます。
